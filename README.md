# wardogs-data

Structured data for the game Wardogs, read from the game's own files: items and vehicles (names, tooltips, icons, sizes, prices, unlocks), weapons, ammunition ballistics, attachments, armor, the damage model, vehicle stats, role skills, event rewards, and per-world maps, buildings, terrain and match objectives. JSON, JSON Schema and CSV, with a data dictionary that describes every field.

Unofficial project, not affiliated with or endorsed by the game's developer or publisher. Released under the [Unlicense](LICENSE); the game's names, numbers and imagery remain the property of the developer and publisher.

## Get the data

| Way | What you get |
| --- | --- |
| **Static API** (GitHub Pages) | Every file under `data/` at `https://warpuppies.github.io/wardogs-data/v1/<path>`, for example `https://warpuppies.github.io/wardogs-data/v1/items.json`. `https://warpuppies.github.io/wardogs-data/v1/index.json` lists every file with its size and checksum. No images. |
| **Release, small zip** | `wardogs-data-<build>.zip`: `data/` (about 8 MB unpacked), this README and the license. |
| **Release, full zip** | `wardogs-data-<build>-full.zip`: everything above plus the item icons and the map tiles and heightmaps of every world (about 600 MB). |
| **Git** | Clone this repository for the data, the README and the license. The images (icons, map tiles) are not in git; they are in the full zip. |

Each zip has a `.sha256` file next to it. The full zip is the only place for the icons and map tiles. The static API serves plain files for one game build at a time, so it has no query parameters; fetch the file and filter it. Pages sends open CORS headers, so a browser app can fetch it directly. It is a best-effort host; for heavy use, download a zip.

```js
const items = await fetch("https://warpuppies.github.io/wardogs-data/v1/items.json").then((r) => r.json());
console.log(items.gameBuild, items.items.length);
```

## Start here

**[`data/README.md`](data/README.md) is the data dictionary.** It is generated from the same schemas that validate the data, so every file, field, unit and CSV column is described there and cannot disagree with the data.

Conventions that hold everywhere: distances are meters and Z is up, ids are the game's own tags and should be compared case-insensitively, and every file records the Steam `gameBuild` it came from.

Worlds: `kavkazi`, `europe`, `north-america`. All distances are meters, Z is up. To place a world position on the map image: `pixel = (world - bounds.min) / image.metersPerPixel`; image rows increase with world Y. Tiles are 256 px WebP files at `assets/maps/<world>/tiles/{z}/{x}/{y}.webp` (z 0 to 6), and the heightmap is `assets/maps/<world>/heightmap.png`.

### Item icons

The full zip holds every icon the data names, in `assets/icons/`, as extracted (PNG, about 21 MB): the `icon` of an item or a buildable and the `weaponIcons` of a vehicle in `vehicles.json`. Each is the path inside that folder, for example `assets/icons/UI/Shared/Icons/Attachments/3D/T_UI_Icon_Attachment_10x_Optic_Textured_512x512.png`. Checksums are in `assets/icons.manifest.json`, which is also in git.

### Map tiles and heightmaps

The full zip holds the built tile pyramid and heightmap of each world in `assets/maps/` (about 570 MB), listed with checksums in `assets/maps.manifest.json`, which is also in git. This is the game's own map imagery.

### Terrain heightmap

`assets/maps/<world>/heightmap.png` is a 16-bit grayscale image (8192 px, about 2 m per pixel), tracked like the tiles. Its own `terrain.json` gives its bounds, which can differ slightly from the map image's bounds. Pixel to height: `z = zRange.min + value / 65535 * (zRange.max - zRange.min)`. Pixel to world: `world = bounds.min + pixel * metersPerPixel`, rows increasing with world Y. Read it as 16-bit; many image libraries silently convert 16-bit grayscale to 8-bit. The `dev` branch has a reference reader (`loadHeightmap`) and `heightAt` for bilinear sampling in `src/maps/terrain.ts`; the build there fails if the decoded terrain does not put the buildings on the ground.

## Helpers for TypeScript

The helpers are public and stable: the functions and schemas exported from `src/lib/index.ts` on the `dev` branch. They are not in this branch, which holds only the data. They are pure functions except `loadWorld`, which reads a world's files.

- `worldToPixel`, `pixelToWorld`: convert between world meters and map image pixels.
- `loadWorld`: loads a world's map, terrain and buildings, with a ground height function.
- `lineOfSight`, `firstObstruction`, `ballisticArc`, `segmentBoxEntry`: line of sight and shell paths against the terrain and the building boxes.
- `fitsSlot`, `itemsFittingSlot`, `tagMatches`: which items a weapon slot accepts, from the slot rules and item tags.
- `valuePerSlot`: price per inventory slot.
- `ItemsFile`, `MapFile`, `BuildingsFile`, `TerrainFile`, `AmmoFile`, `AttachmentsFile`, `DamageFile`, `EquipmentFile`, `ChallengeRewardsFile`, `RewardsFile`, `RolesFile`, `SkillsFile`, `VehiclesFile`, `WeaponsFile`: zod schemas that parse each data file into typed values.

```ts
import { ballisticArc, firstObstruction, itemsFittingSlot, lineOfSight, loadWorld } from "./src/lib/index.js";

const world = await loadWorld("kavkazi");
const options = { terrain: world.groundHeight, buildings: world.buildings };

lineOfSight([-8000, -11000, -900], [-7800, -11100, -905], options);           // true when nothing blocks the line
itemsFittingSlot(akSlot, items);                                              // the scopes, magazines or ammo a slot takes
firstObstruction(ballisticArc(from, to, 150), options);                       // what blocks a shell with a 150 m apex, and where
```

Building boxes enclose their buildings, so they can block a path that really slips past a roof edge; destroyed buildings are not modeled. Terrain is sampled every metre along the path from a heightmap of about 2 m resolution, which suits artillery ranges but not individual walls.

## About this repository

`main` holds only the data and its assets. The `dev` branch adds the pipeline that builds the data from a local game install, its tests and the helpers; see `DEVELOPING.md` there. Everything under `data/` is generated and checked against `data/MANIFEST.json`, so it is never edited by hand.
